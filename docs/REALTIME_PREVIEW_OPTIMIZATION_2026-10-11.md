# 实时预览流畅度优化复盘（2026-10-11）

## 范围与目标

本轮从上游 `Aa488/my-robot` 的 `wham_gmr_win` 最新提交 `ce9a28b` 开始，在独立分支 [`perf/wham-gmr-realtime-latest-2026-10-11`](https://github.com/xinxinrana/my-robot/tree/perf/wham-gmr-realtime-latest-2026-10-11) 上工作，提交到自己的仓库 `xinxinrana/my-robot`。目标是让评委看到的人体动作和机器人动作按尽量均匀的时间间隔更新，减少短时间扎堆出帧及长时间停顿。本文只评价本轮 Docker 浏览器预览路径；没有启动或修改 Unity。

评价流畅度不能只看平均 FPS。还需看相邻显示帧的 p95 间隔、源帧年龄、处理端到端延迟、跳过的展示时隙，以及机器人动作是否滞后于真人。显示层可以平滑已有姿态、跳过过时帧，却不能凭空补出模型尚未计算出的新动作。

## 判断过程与实现

1. **先找实际展示瓶颈。** 最初的生产端实验把人体和机器人分开提速，并降低机器人渲染分辨率。但检查预览接收端后发现：网页每 300 ms 才轮询一次图片，最高只能看到约 3.3 次更新/秒，而且两路没有统一的展示时钟。这个实验由 `f692947` 撤回，保留原始分辨率，再从接收端和展示时序入手。
2. **接收端只保留最新帧。** 新增仓库内的 TCP 接收与 HTTP 预览服务，每路只存最新 JPEG；慢客户端直接跳到最新帧，不重放历史队列。先提供 MJPEG 推流。实机的 360 Chrome 变体对有效 MJPEG 仍显示破图，因此网页改用长轮询获取“比上次序号更新”的单帧 JPEG，MJPEG 接口继续保留。浏览器需要刷新页面才会加载新脚本。
3. **展示时钟与生产时钟解耦。** 实时摄像头、TCP 预览、无本地窗口和录像的模式下，使用单调时钟，以 15 FPS 为目标安排展示时隙；只读取最新摄像头帧和最新机器人姿态，错过时隙就跳过，发送后也保持最小时间间隔。仅对显示用的机器人姿态做短响应时间平滑和根旋转最短弧插值；IK、CSV、PKL、模型输出与原始渲染尺寸不改。旧行为可由 `TCP_PRESENT_CLOCK=0` 切回。
4. **接通本机实测链路。** Windows Docker 不能直接透传本机 USB 摄像头，所以加入 `WHAM_CAMERA_URL` 读取主机上的 MJPEG 桥接；`WHAM_TCP_HOST`/`WHAM_TCP_PORT` 让容器连接主机预览服务。补上 Windows 检出文件的 CRLF 兼容，解决 Linux 镜像启动脚本解释错误。这些是让同一代码可以运行和验证的接线修改，本身不是速度收益。
5. **分段计时。** 最后分别记录 MuJoCo 机器人渲染、摄像头 TCP 发送、机器人 TCP 发送和完整展示时隙的滚动 p95，避免将发送延迟误判成 GPU 渲染延迟。

## 现场结果与局限

本机为 RTX 2060 6 GB，摄像头经 Windows 主机 MJPEG 桥接进入 Docker，浏览器预览由主机服务提供。下列数字来自短时运行日志，适合定位瓶颈，不构成统一动作样本、长时间运行的正式 A/B 验收。

| 条件或指标 | 观察 |
| --- | --- |
| 启用可选 GPU 调度器 | WHAM 约 2 FPS，处理延迟约 1.5 秒；预览 p95 间隔约 1.6–1.7 秒。 |
| 关闭可选 GPU 调度器（当前运行配置） | WHAM 约 5–6 FPS，处理延迟约 0.4–0.6 秒，GPU 等待明显减少；这是运行参数选择，不是本轮代码的独立提速提交。 |
| 当前两路预览 | 到达间隔 p95 仍约 1.8–2.0 秒，肉眼仍会感到停顿；15 FPS 是时钟目标，不是实得 FPS。 |
| 分段计时 | MuJoCo 渲染 p95 约 2–3 秒；两路 TCP 发送通常仅数毫秒。单一展示线程先渲染机器人，再发送两路画面，因此慢渲染也拖住摄像头展示。 |
| 接口与回归 | 两路 `/frame` 返回 HTTP 200，JPEG 分别可解码为 360×640 和 405×720；Python 单元测试 10 项通过。 |

因此，本轮完成了过时帧丢弃、定时展示、浏览器接收兼容和可观测性，但**还没有达到评委期待的均匀机器人运动**。下一步应先将 `viewer.step`、`renderer.update_scene`、`renderer.render` 和图像转换进一步分段测量，再处理真实渲染开销，并让摄像头传输不被机器人渲染阻塞。若考虑降低渲染分辨率，须在同一场景下同时比较画质与帧间隔后再决定。没有完成 30–60 分钟的持续出帧验收，也没有验证 Unity 端的 CSV 延迟。
